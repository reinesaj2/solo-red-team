This document provides detailed explanations of the theoretical prerequisites required before engaging with password cracking tools, as specified in Project 3 Section 3.2.

1. THE ROLE OF ONE-WAYNESS IN PASSWORD HASHING
==============================================

Definition and Purpose:
One-wayness (also called "preimage resistance") is the fundamental cryptographic property that makes it computationally infeasible to reverse a hash function. Given a hash value h, it should be extremely difficult to find any input x such that hash(x) = h.

Why One-Wayness Matters for Passwords:
- **Storage Security**: Systems store hash(password) instead of password itself
- **Breach Protection**: Even if hash database is stolen, passwords remain protected
- **Authentication Process**: System compares hash(entered_password) with stored hash
- **Non-Reversibility**: Administrators cannot recover original passwords from hashes

Mathematical Foundation:
For a secure hash function H:
- Easy to compute: H(password) = hash_value
- Hard to reverse: Given hash_value, finding password is computationally infeasible
- Collision resistant: Finding two different passwords with same hash is extremely difficult

Real-World Application in This Project:
- **Windows NTLM**: Uses MD4, which has weakened one-wayness properties
- **Linux SHA-512**: Strong one-wayness makes direct reversal impossible
- **Attack Strategy**: Since reversal is impossible, we use dictionary/brute force methods

2. THE ROLE OF SALT IN PASSWORD HASHING
=======================================

Definition:
Salt is a random value added to a password before hashing, making the final hash unique even for identical passwords across different accounts or systems.

Mathematical Representation:
- Without salt: hash_value = H(password)
- With salt: hash_value = H(password || salt) where || means concatenation

Purpose and Benefits:

A) **Rainbow Table Prevention**:
- Rainbow tables are precomputed hash-to-password mappings
- Salt forces attackers to compute fresh hashes for each password attempt
- Example: "password" + salt "a1b2" → different hash than "password" + salt "x9z8"

B) **Identical Password Protection**:
- Two users with password "123456" will have different hashes due to different salts
- Prevents pattern recognition across password database
- Protects privacy even within same system

C) **Attack Amplification Prevention**:
- Without salt: crack one hash → potentially helps crack all identical passwords
- With salt: each hash must be attacked individually

Examples from This Project:

**No Salt (Windows NTLM)**:
- Same password = same hash across all users
- Rainbow tables highly effective (as seen with Ophcrack success)
- Pattern recognition reveals duplicate passwords

**Individual Salt (Linux SHA-512)**:
- Format: $6$salt$hash where salt is unique per user
- Example: Morpheus and Neo could both use "password" but have completely different hashes
- Forces individual attack on each user account

3. THE ROLE OF ITERATION COUNT IN PASSWORD HASHING
==================================================

Definition:
Iteration count (also called "work factor" or "cost parameter") specifies how many times the hash function is applied, intentionally slowing down the hashing process.

Mathematical Representation:
v = h^iteration_count(password || salt)

Where h^n means applying hash function h exactly n times:
- h^1(input) = h(input)
- h^2(input) = h(h(input))
- h^5000(input) = h(h(h(...h(input)...))) [5000 applications]

Purpose and Security Benefits:

A) **Time-Memory Tradeoff**:
- Makes each password attempt computationally expensive
- Legitimate authentication: 5000 iterations = ~0.01 seconds (acceptable)
- Brute force attack: 5000 iterations × millions of attempts = very expensive

B) **Moore's Law Adaptation**:
- As computers get faster, iteration count can be increased
- Maintains security margin against improving hardware
- Example: 1000 iterations (2010) → 5000 iterations (2020) → 10000 iterations (future)

C) **Attack Economics**:
- Without iterations: millions of password attempts per second
- With iterations: hundreds or thousands of attempts per second
- Changes attack feasibility from "easy" to "computationally expensive"

Examples from This Project:

**Single Iteration (Windows)**:
- NTLM: MD4(password) - no iteration count
- LM: DES-based with minimal computational cost
- Result: Very fast dictionary attacks (thousands of attempts/second)

**5000 Iterations (Linux)**:
- SHA-512 applied 5000 times per password attempt
- Our testing: ~5 attempts/second vs thousands for Windows
- Result: Computationally protected against extensive brute force

4. UNDERSTANDING v = h^50,000(w||s)
==================================

Mathematical Breakdown:

Components:
- **v**: The final hash value (verification data stored in system)
- **h**: The cryptographic hash function (e.g., SHA-512, MD5, etc.)  
- **50,000**: The iteration count (number of times hash function is applied)
- **w**: The password (what the user types)
- **s**: The salt (random value unique to this password)
- **||**: Concatenation operator (joining two strings together)

Step-by-Step Process:
1. **Input Preparation**: Combine password with salt → "password123salt_a1b2c3"
2. **First Iteration**: h¹(w||s) = h("password123salt_a1b2c3") 
3. **Second Iteration**: h²(w||s) = h(result_from_step_2)
4. **Continue**: Repeat hashing process exactly 50,000 times
5. **Final Result**: v = the output after 50,000 iterations

Real-World Example:
If w="mypass", s="xyz789", h=SHA-256, iterations=50,000:
- Round 1: SHA-256("mypassxyz789") = "a1b2c3..."
- Round 2: SHA-256("a1b2c3...") = "d4e5f6..."
- ...continue for 50,000 rounds...
- Round 50,000: SHA-256(previous_result) = v (final stored hash)

Why 50,000 Iterations:
- **Security Margin**: Makes brute force attacks 50,000x more expensive
- **Practical Balance**: Still fast enough for legitimate authentication (~50ms)
- **Future Proofing**: Can be increased as computers become more powerful

5. LM PASSWORD HASH GENERATION PROCESS
======================================

LM (LAN Manager) Hash Algorithm - Legacy Windows Authentication:

Step-by-Step Process:

**Step 1: Password Preparation**
- Convert password to uppercase (case insensitive)
- Example: "MyPassword" → "MYPASSWORD"
- Pad or truncate to exactly 14 characters
- Example: "MYPASSWORD" → "MYPASSWORD    " (padded with spaces)

**Step 2: Split Password**
- Divide 14-character password into two 7-character halves
- Half 1: "MYPASSE" (characters 1-7)
- Half 2: "WORD   " (characters 8-14, space-padded)

**Step 3: DES Key Generation**
- Convert each 7-character half into a 56-bit DES key
- Use specific bit manipulation to create proper DES key format
- Results in two separate 56-bit DES keys

**Step 4: DES Encryption**
- Encrypt fixed plaintext "KGS!@#$%" using each DES key
- Key1: DES("KGS!@#$%", key_from_first_half) = result1
- Key2: DES("KGS!@#$%", key_from_second_half) = result2

**Step 5: Concatenation**
- Combine both 8-byte DES results
- Final LM hash = result1 || result2 (16 bytes total)

Critical Vulnerabilities:

A) **Case Insensitivity**: "Password" and "PASSWORD" produce identical hashes
B) **14-Character Limit**: Longer passwords truncated, shorter passwords padded
C) **7-Character Splits**: Each half can be attacked independently (2^28 vs 2^56 complexity)
D) **No Salt**: Identical passwords always produce identical hashes
E) **Weak Algorithm**: DES with 56-bit keys vulnerable to modern attacks
F) **Fixed Plaintext**: Same target "KGS!@#$%" used for all passwords

Why Ophcrack Was So Successful:
- Rainbow tables precomputed for all possible 7-character combinations
- Case insensitivity reduces keyspace dramatically
- 7-character split allows parallel attack on both halves
- No salt means universal rainbow tables work for all systems

6. NTLM PASSWORD HASH GENERATION PROCESS
========================================

NTLM (NT LAN Manager) Hash Algorithm - Modern Windows Authentication:

Step-by-Step Process:

**Step 1: Unicode Conversion**
- Convert password to UTF-16 Little Endian encoding
- Preserves case sensitivity and international characters
- Example: "Password" → [50 00 61 00 73 00 73 00 77 00 6f 00 72 00 64 00] (hex)

**Step 2: MD4 Hashing**
- Apply MD4 hash function to UTF-16 encoded password
- MD4 produces 128-bit (16-byte) hash output
- Example: MD4(UTF16("Password")) → 8846f7eaee8fb117ad06bdd830b7586c

**Step 3: Final Hash**
- The MD4 output IS the final NTLM hash
- No additional processing, iterations, or salt
- Stored in SAM database for authentication

Advantages over LM:
- **Case Sensitive**: "Password" ≠ "password" ≠ "PASSWORD"
- **No Length Limit**: Supports passwords longer than 14 characters  
- **No Splitting**: Entire password hashed as single unit
- **Unicode Support**: International characters fully supported

Remaining Vulnerabilities:
- **No Salt**: Identical passwords still produce identical hashes
- **Single Iteration**: MD4 applied only once (very fast to compute)
- **Weak Algorithm**: MD4 has known cryptographic weaknesses
- **Speed**: Modern GPUs can compute billions of MD4 hashes per second

Why Dictionary Attacks Succeeded:
- No salt allows rainbow table attacks
- Single iteration makes brute force very fast
- Common passwords in wordlists (rockyou.txt was highly effective)
- MD4 weakness doesn't prevent dictionary attacks

7. LINUX PASSWORD HASH GENERATION PROCESS
=========================================

Modern Linux Password Hashing (SHA-512 crypt):

Step-by-Step Process:

**Step 1: Salt Generation**
- Generate random 16-character salt
- Uses base64-like encoding: ./0-9A-Za-z
- Example: "abcdefghijklmnop"
- Salt is unique for each password, even on same system

**Step 2: Initial Hash**
- Combine password + salt + password
- Example: "mypass" + "abcd...nop" + "mypass"
- Apply SHA-512: initial_hash = SHA-512(password || salt || password)

**Step 3: Iteration Process**
- Apply SHA-512 exactly 5000 times (default for $6$ format)
- Each iteration: hash = SHA-512(hash)
- This is the "key stretching" process
- Takes ~5000x longer than single SHA-512 computation

**Step 4: Base64 Encoding**  
- Convert final 512-bit hash to base64-like encoding
- Results in 86-character encoded string
- Uses custom alphabet: ./0-9A-Za-z

**Step 5: Format Assembly**
- Final format: $6$salt$hash
- $6 = identifier for SHA-512 crypt
- Example: $6$abcdefghijklmnop$encodedHashValue

Security Features:

A) **Individual Salt**:
- Every password gets unique salt
- Prevents rainbow table attacks
- Same password on different accounts = completely different hashes

B) **Key Stretching (5000 iterations)**:
- Makes each password attempt computationally expensive
- ~0.2 seconds per attempt vs microseconds for unsalted hashes
- Scales attack time from hours to years for brute force

C) **Strong Hash Function**:
- SHA-512 has no known practical attacks
- 512-bit output provides enormous hash space
- Collision resistance prevents hash duplication attacks

D) **Configurable Cost**:
- Iteration count can be increased as hardware improves
- Modern systems may use 10,000+ iterations
- Future-proofed against computational advances

Why Our Attacks Mostly Failed:
- Individual salts prevented rainbow table use
- 5000 iterations made brute force computationally expensive  
- Strong SHA-512 algorithm resisted cryptographic attacks
- Only one password cracked due to strategic dictionary hit

COMPARATIVE SECURITY ANALYSIS
=============================

Security Ranking (Strongest to Weakest):
1. **Linux SHA-512**: Salt + iterations + strong hash function
2. **Windows NTLM**: Strong hash function, but no salt/iterations  
3. **Windows LM**: Multiple fundamental vulnerabilities

Attack Difficulty Ranking:
1. **LM**: Minutes (rainbow tables)
2. **NTLM**: Minutes to hours (dictionary attacks)
3. **SHA-512**: Days to years (limited by computational cost)

This demonstrates the evolution of password security from fundamentally flawed (LM) to computationally secure (SHA-512) approaches, validating the core learning objectives of CS 660 Project 3.
